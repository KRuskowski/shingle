## 2. Native backend

Add DRM/KMS and libinput with careful failure handling. The design is [design/native-backend.md](design/native-backend.md).

In short, the interactive frontend moves out of `shingle-nested` into a shared `shingle-frontend` crate, and `shingle-render` loses winit. A single `shingle` binary picks its backend like Wayfire: nested inside a Wayland session, native from a TTY. The native backend uses libseat for the session and VT switching and libinput for input, and drives atomic KMS itself through the `drm` crate, rendering zero-copy into GBM buffers imported into wgpu, with a dumb-buffer copy fallback. Native code is built and unit-tested on this host but only ever run on a dedicated test machine, which is being set up; no VMs. The work is split into ten workspaces, each with acceptance criteria in the design:

1. NB-1 `shingle-render-targets`: shared GPU context and render targets, no winit in `shingle-render`. Done ([status.md](status.md#compositor-and-renderer)).

4. NB-4 `shingle-frontend-host`: done; `App` is `shingle_frontend::Frontend` behind the `Host` trait and `InputEvent`, nested is a thin winit host, and key repeat is the frontend's own timer. See [status.md](status.md#compositor-and-renderer) and [status.md](status.md#with-real-clients).
5. NB-5 `shingle-input-registry`: done; see [status.md](status.md#backend-host-api).
6. NB-6 `shingle-native-session`: built and unit-tested through fakes: `shingle-native` runs the frontend with libseat, libinput and VT switching and draws offscreen, and `shingle` runs it from a VT login and refuses SSH logins ([status.md](status.md#native-backend-seat-and-input)). ## 3. DMA-BUF

Add DMA-BUF import and remove unnecessary CPU texture copies. The design is [design/dmabuf.md](design/dmabuf.md), from 2026-11-25; its open questions were decided with defaults on the operator's behalf ([Decisions](design/dmabuf.md#decisions)).

In short:

- **Vulkan setup.** `shingle-render` opens its device through wgpu-hal with the DMA-BUF feature, `VK_EXT_queue_family_foreign` and `VK_KHR_external_semaphore_fd`, queries which single-plane modifiers Vulkan can import and render to, and has one import call for client buffers and for NB-8's scanout buffers.
- **Protocol.** `zwp_linux_dmabuf_v1` version 5 with feedback naming the render node, real test imports at `create`, textures cached per buffer. `wl_drm` is not offered: Mesa, Xwayland and NVIDIA's EGL find the device through the feedback.
- **Sync.** Implicit sync by polling the buffer's fds before a commit applies, and `linux-drm-syncobj-v1`, which Wayfire lacks but this host's NVIDIA clients need. Buffers are released only after the GPU has finished reading them.
- **CPU copies.** `wl_shm` buffers are uploaded from the client's mapping, damaged rows only, without the RGBA copy and swizzle; screencopy captures the rendered frame.
- **Testing.** A new GPU offscreen backend lets real NVIDIA clients and nested Shingle run in a namespace with a private `/dev` that holds only the render node, never touching the host's display.

The work is split into seven workspaces, DB-1 to DB-7, each with acceptance criteria in the design: Vulkan setup, offscreen backend and GPU harness, buffer lifetime, `zwp_linux_dmabuf_v1`, `linux-drm-syncobj-v1`, shm uploads without copies, and later direct scanout of client buffers. NB-8 builds on DB-1.

DB-1 `shingle-gpu-dmabuf` is done ([status.md](status.md#compositor-and-renderer), [design/dmabuf.md](design/dmabuf.md#db-1-as-built)). DB-2 `shingle-offscreen-backend` is done too ([status.md](status.md#the-shingle-binary), [design/dmabuf.md](design/dmabuf.md#db-2-as-built)): `shingle --backend offscreen`, screencopy from drawn frames, and `tools/gpu_test/run.py --checks`, which records that without linux-dmabuf NVIDIA's Vulkan WSI cannot present and its EGL is not used. DB-3 `shingle-buffer-lifetime` is done ([status.md](status.md#compositor-and-renderer), [design/dmabuf.md](design/dmabuf.md#db-3-as-built)): buffer content, reference-counted buffer locks with release on the last drop, the per-surface commit queue with its blocker interface, and the fix for buffers replaced behind a FIFO barrier, a commit-timing deadline or a synchronized parent, which were never released. DB-4 `shingle-linux-dmabuf` is done ([status.md](status.md#compositor-and-renderer), [design/dmabuf.md](design/dmabuf.md#db-4-as-built)): `zwp_linux_dmabuf_v1` version 5 with feedback on the render node, real test imports at `create`, textures cached per buffer, release after the GPU, the implicit-sync wait and clients started after the renderer. In the GPU namespace Vulkan clients, Chromium, Xwayland's glamor, `weston-simple-dmabuf-egl` and nested Shingle present DMA-BUFs; NVIDIA's EGL clients still need a run with the card node, on the test machine. Found and fixed while checking it: FIFO and commit-timing updates were merged rather than queued, which let NVIDIA's Vulkan clients run ahead of their commit-timing deadlines and freeze about one run in six; they now queue in order with their own gates and deadlines, as wlroots does, and the vkcube checks passed 10 runs out of 10 ([design/dmabuf.md](design/dmabuf.md#db-3-as-built)). DB-5 `shingle-drm-syncobj` is done ([status.md](status.md#compositor-and-renderer), [design/dmabuf.md](design/dmabuf.md#db-5-as-built)): `wp_linux_drm_syncobj_manager_v1` on the render node, every protocol error, acquire waits on eventfds in the commit queue and release points signalled with the buffer's release. In the GPU namespace NVIDIA's Vulkan clients, Xwayland's glamor, nested Shingle and Chromium commit with syncobj points, and a surface stalled on an acquire point stops only itself; NVIDIA's EGL clients with syncobj, like their DMA-BUFs, wait for the test machine (step 24 of [native-testing.md](native-testing.md)). DB-6 `shingle-shm-upload` is done ([status.md](status.md#compositor-and-renderer), [design/dmabuf.md](design/dmabuf.md#db-6-as-built)): shm buffers are uploaded from the client's pool in their own byte order, damaged rectangles only, right after their commit, and given back before any frame; sealed pools stay mapped, and in the measured runs offscreen Shingle's CPU time for full-output shm frames fell to about a quarter in release builds and two fifths in debug builds. DB-7, direct scanout of client buffers, is later and optional and needs the test machine; NB-8 and NB-10, which it builds on, are built ([design/dmabuf.md](design/dmabuf.md#nb-8-as-built), [NB-10](design/native-backend.md#nb-10-as-built)).

## 4. XWayland

Run X11 applications through a rootless `Xwayland` with Shingle's own X window manager. The design is [design/xwayland.md](design/xwayland.md), from 2026-11-25; the operator has decided its open questions ([Decisions](design/xwayland.md#decisions)).

In short:

- **Server.** Shingle binds the X display (`:N`, lock file, filesystem and abstract sockets) when it starts. It execs `Xwayland -rootless` with `-listenfd`, `-wm` and `-displayfd`, eagerly or on the first connection. The new option `xwayland.mode` takes Wayfire's `true`, `false` and `lazy`, and is imported from `[core] xwayland`.
- **Environment.** `DISPLAY` goes into every child's environment and into `stipc/get_display`. Since XW-1 every child gets one client environment, and the host's `DISPLAY` no longer reaches nested children.
- **XWM.** The XWM uses `x11rb` 0.14 (pure Rust) in a new `shingle-xwayland` crate and ports the ICCCM/EWMH subset of wlroots' XWM, which Wayfire uses. Surfaces are associated only through `xwayland_shell_v1`, which needs Xwayland 23.1 or newer.
- **Window model.** X11 toplevels share `ToplevelRole` with xdg toplevels through a `ToplevelHandle` enum. Tiling, rules, Scale, Expo, IPC and sessions work unchanged: `app-id` comes from the `WM_CLASS` class, and the PID from XRes. Override-redirect windows are drawn unmanaged above the Top layer.
- **Selections, drag and drop, and scaling.** Clipboard and primary selection are bridged both ways, and so is drag and drop. Scaling matches Wayfire: X11 clients are blurry above scale 1.
- **Testing.** Real-client tests run inside a user, mount, network and PID namespace with a private `/tmp/.X11-unix`.

The work is split into seven workspaces, each with acceptance criteria in the design:

1. XW-1 `shingle-toplevel-handle`: done; the toplevel role is shell-neutral and every child gets one client environment, which stopped the host `DISPLAY` and `WAYFIRE_SOCKET` leaks. See [status.md](status.md#the-shingle-binary) and [status.md](status.md#with-real-clients).
2. XW-2 `shingle-xwayland-server`: done; Shingle binds its X display, supervises Xwayland (eager or lazy, with the restart rule) and brings its XWM up; `DISPLAY`, the `stipc` display methods, `xwayland-ready` and the startup script work. See [status.md](status.md#with-real-clients).
3. XW-3 `shingle-xwayland-windows`: done; `xwayland_shell_v1` pairs X windows with surfaces, and managed X11 toplevels are Shingle windows with configure, `_NET_WM_STATE`, close, IPC (class, title, PID) and session identity. See [status.md](status.md#with-real-clients).
4. XW-4 `shingle-xwayland-behaviour`: done; ICCCM focus and the `FocusIn` guard, `_NET_ACTIVE_WINDOW`, `_NET_WM_STATE` both ways, `WM_CHANGE_STATE`, move, resize and close requests, X stacking, transients and dialogs, override-redirect windows in the Unmanaged layer and the root cursor; Scale, Expo, the switchers, rules and session restore checked with X windows. See [status.md](status.md#with-real-clients).
5. XW-5 `shingle-xwayland-selection`: done; the clipboard and primary selection are bridged between X and Wayland in both directions, with INCR and without blocking the compositor, and wlr-data-control clients see X selections. See [status.md](status.md#with-real-clients).
6. XW-6 `shingle-xwayland-dnd`: done; drag and drop is bridged between X and Wayland in both directions over Xdnd, through a proxy window for X sources over Wayland windows, and X drag icons are drawn above everything. See [status.md](status.md#with-real-clients).
7. XW-7 `shingle-xwayland-hidpi`: optional zero-scaling HiDPI mode.

XW-6 is done; XW-7, the optional zero-scaling mode, is what remains of XWayland; it was deferred until after the multi-output item ([design/xwayland.md](design/xwayland.md#decisions)). The harness's intermittent SIGTERM failures were a session write that took more than 10 s on the busy disk; the X display is now freed before it, and the harness waits up to 60 s. Session writes while Shingle runs have since moved to a background thread, so the disk no longer stalls the compositor ([status.md](status.md#sessions)).

## 5. Multi-output

Complete output lifecycle, focus, workspaces, sessions and rendering across outputs, including headless outputs over IPC where Wayfire offers them. The design is [design/multi-output.md](design/multi-output.md), from 2026-11-26; its open questions were decided with the proposed defaults on the operator's behalf ([Decisions](design/multi-output.md#decisions)).

In short:

- **Model.** The compositor keeps a map of outputs, each with its own rectangle, scale, transform, IPC id, `wl_output` global and protocol state. `[output:NAME] position` gains Wayfire's default `auto`, placed as wlroots does.
- **Workspace sets.** The core separates workspace sets (Wayfire's wsets, each with a tiling tree per workspace) from outputs; each output shows one set, and a set without an output is parked.
- **Focus and moving views.** One active output, changed by a click, a touch, a focused view, `oswitch` or IPC, as in Wayfire. Views move between outputs with Wayfire's `move_view_to_output` rules, through `oswitch`, IPC, `wsets`, `start_on_output` and drags.
- **Unplug and replug.** `output_layout.unplug` is `move` (Wayfire's default), `park` (Wayfire's preserve-output) or `return` (proposed default: windows join the active output and go back to their trees when the monitor returns, matched by EDID identity, else by name). Sessions store sets with their output's name and identity.
- **Rendering.** One scene per output, clipped to it; frame callbacks per output and presentation from each surface's primary output. Nested opens one window per output, native lights one CRTC per output with wlroots' CRTC matching and combined `TEST_ONLY` modesets, and headless and offscreen take `--outputs N`.
- **IPC.** Real output ids and wset indices, six new methods (headless and nested outputs, `wsets`) and six new events, and Wayfire's payloads for `output-layout-changed` and `wset-workspace-changed`.

The work is split into seven workspaces, MO-1 to MO-7, each with acceptance criteria in the design: core workspace sets and sessions, the compositor's output registry, client protocols per output, focus and moving views, the frontend's scenes per output with the offscreen backend, nested windows, and native multi-CRTC. All but MO-7 are verified on this host with headless, offscreen and nested Shingle inside the harness namespaces; MO-7 is built and unit-tested through the fake card and needs the test machine for the rest. Mirroring is a later, optional MO-8.

2. MO-2 `shingle-output-registry`: done; the compositor's output registry with a global, xdg-output and output-management head per output, the layout, unplug policies, restored sessions settling on the outputs, IPC ids, `wayfire/create-headless-output` and `destroy-headless-output`, the output events and headless `--outputs N` ([status.md](status.md#several-outputs), [MO-2 as built](design/multi-output.md#mo-2-as-built)).
3. MO-3 `shingle-output-protocols`: done; enter and leave by visibility with each output's scales, the primary output for presentation, FIFO and commit timing, layer and lock surfaces per output, screencopy in output coordinates and physical pixels, outputs turned off and on through output management, power and gamma per output, ext-workspace groups and foreign-toplevel output events per output, and the probe's `--report-outputs` and `--layer` ([status.md](status.md#several-outputs), [MO-3 as built](design/multi-output.md#mo-3-as-built)).

MO-4 `shingle-output-focus`: done; the active output and `output-gain-focus`, the pointer kept on the layout, `oswitch` and `wsets` bindings, moving windows between outputs and sets with Wayfire's geometry (`configure-view` with `output_id`, `start_on_output`, `set_fullscreen` on an output, drags, unplug transfers), `view-set-output` and `view-wset-changed`, vswitch and activators with an output, `simple-tile` layouts by `wset-index` and the `wsets` IPC methods ([status.md](status.md#several-outputs), [MO-4 as built](design/multi-output.md#mo-4-as-built)).

## 8. Application launcher

The operator's own wish (2026-11-26): a launcher that combines rofi's quick type-to-run with the KDE start menu's in-place customization. rofi is fast to use but hard to style and only configurable through files; KDE's menu can be rearranged to taste while it is open. The goal is one launcher that starts as fast as rofi from a keybinding, and lets entries be pinned, renamed, reordered, grouped and hidden directly in the open menu, with every change saved at once and no config file to edit by hand.

What the operator values in each (2026-11-26): from rofi, its speed, type-to-search and that it works with the keyboard alone; from KDE, adding shortcuts in place, categories, and marking favourites. Both must hold at once: the keyboard path stays as fast as rofi even with categories and favourites shown.

Not designed yet.
