# Development

## Requirements

- Rust 1.92 or newer (edition 2024).
- Development headers for Wayland, xkbcommon and PAM, and for the native backend libinput, libseat, udev, libdrm and GBM. On Debian: `libwayland-dev libxkbcommon-dev libpam0g-dev libinput-dev libseat-dev libudev-dev libdrm-dev libgbm-dev`.
- A Vulkan-capable GPU and driver for wgpu.

## Build, test and lint

```sh
cargo build --workspace
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
```

To be sure that no test reaches a GPU, input or VT device of the host, run the suite in a namespace whose `/dev` has none, with lavapipe as the only Vulkan driver: `bwrap --bind / / --dev /dev env VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json cargo test --workspace --no-fail-fast`. The three reference-image tests in crates/shingle-render/tests/offscreen_pixels.rs then fail, because their references were rendered on a hardware GPU; everything else passes, and the udmabuf tests in crates/shingle-render/tests/dmabuf_import.rs skip.

To run a GPU test on the render node without exposing anything else, use tools/gpu_test/run.py: it runs one command in a user, mount, network and PID namespace whose `/dev` holds only the render node, NVIDIA's compute nodes, `udmabuf` and the basic nodes, and fails if any process opens another device. For example `cargo test -p shingle-render --test dmabuf_import --no-run`, then `tools/gpu_test/run.py -- target/debug/deps/dmabuf_import-HASH --include-ignored`. `cargo run -p shingle-render --example dmabuf_caps` prints which formats and modifiers each Vulkan adapter can import. The application compatibility sweep is one command, after `cargo build -p shingle-bin` and `cargo build -p shingle --example wl_probe`: `nice -n 19 tools/gpu_test/run.py --checks apps` (or `app-NAME` for one of kitty, konsole, kate, dolphin, okular, evince, mpv, vlc, gimp, inkscape, libreoffice, firefox, chromium, google-chrome, rofi and dunst; `--captures DIR` keeps a capture of every step as `NAME-NN-STEP.ppm`, and the application's `WAYLAND_DEBUG` output and Shingle's log as `NAME-client.log` and `NAME-shingle.log`). tools/gpu_test/app_checks.py starts each installed application, one at a time, against its own offscreen Shingle with two outputs (`--outputs 2`) and two workspaces, Xwayland on demand, a distinctive background colour and 24-pixel gaps. Each application gets a private HOME, config, data and cache directory with a fresh profile, a private D-Bus session bus that activates nothing (with /run/dbus covered so the host's system bus is unreachable), no network, `WAYLAND_DEBUG=1`, and runs as the caller's uid in a nested user namespace (VLC refuses to run as root). A scenario then drives it over IPC and STIPC input: it must map and tile, draw its whole view and nothing in the gaps, take the keyboard focus, take typed text (a shell command a terminal runs, text an editor copies back to `wl-paste`, a `data:` URL that paints a browser's page), open a popup by a right click and close it with Escape, open a dialog by its shortcut that is a child of the main window, floats centred on it, takes the focus and closes with Escape, paste from `wl-copy` and copy to `wl-paste`, redraw when the tiler halves it beside a `wl_probe` and when a Super+right drag moves the boundary, go fullscreen and back, leave the first workspace for the second and come back, move to the second output and back, and close. Captures are judged for blank content, Shingle's background inside the view (a client that did not redraw at its new size) and content in the gaps (GTK's translucent shadows count as background); the client's log is searched for `wl_display.error` and crashes. rofi, an X11 client, must cover the middle of the output over a tiled probe, take typed text without being a managed view and run the command; dunst must own `org.freedesktop.Notifications` on the private bus, show a `notify-send` notification in its layer surface and take it away after its timeout. Each step is a PASS or FAIL line, or INFO for what does not apply, and the end prints the per-app table recorded in [status.md](status.md#applications). Before each application the 1-minute load must be under 12. After each application every process that appeared in the namespace since it started is ended through `run.signal_checked` with its own comm. Steam is not part of the sweep: it needs the network to install its runtime and an account. `python3 -m unittest test_app_checks` in tools/gpu_test tests the pure helpers.

Time to first frame of new tiled windows: `tools/gpu_test/run.py --checks first-frame` starts kitty, foot and Firefox beside a tiled probe and reports, from their `WAYLAND_DEBUG` logs, the milliseconds to their first configure, first buffer and first buffer at the tile's size (tools/gpu_test/first_frame_checks.py). foot is not installed on this host; `apt-get download foot libfcft4t64 libutf8proc3`, `dpkg -x` each into a directory under the workspace, and pass `SHINGLE_FOOT=DIR/usr/bin/foot` (its libraries are found beside it). To compare with an earlier build, pass that build's binaries with `--binary` and `--wl-probe`.

tools/output_test/run.py runs headless Shingle and its real-client checks in the same kind of namespace, `--checks NAME ...` picking groups by function name. Its WG-4 groups `wg4_headless_checks` and `wg4_offscreen_checks` (tools/output_test/wayfire_shell_checks.py) bind `zwf_shell_manager_v2` from a Python client that speaks the Wayland wire protocol itself (tools/output_test/wayland_wire.py, unit-tested by `python3 -m unittest` there): hotspots, the fullscreen events of a `wl_probe --fullscreen` and `toggle_menu` against headless Shingle with two outputs, and `interactive_move` against offscreen Shingle on lavapipe, which, unlike headless, runs moves. WG-8's group `wg8_text_input_checks` (tools/output_test/text_input_checks.py) runs a raw-protocol application with a `zwp_text_input_v1` and test input methods on input-method v1 and v2 against headless Shingle: activation, the state reaching the input method, and the committed text arriving at the application with its serial.

After `cargo build -p shingle-bin` and `cargo build -p shingle --example wl_probe`, `tools/session_test/run.py` checks that a slow disk does not stall Shingle: in the output harness's namespace it runs nested Shingle on lavapipe inside a headless one, with `XDG_STATE_HOME` on a FUSE mount (tools/session_test/slowfs.py, python3-fuse) whose fsync sleeps `--delay` seconds (1.5 by default), changes the layout over IPC every 100 ms for 3 s while a session write is stuck, first as a warm-up and then timed, and requires every timed reply within 50 ms, few coalesced writes, nested's main thread under 10 % of a CPU in the 2 s after, a clean SIGTERM exit and the last layout in the session file. The warm-up is there because lavapipe compiles the shaders of each draw state on first use, which holds nested's frame for 50 to 90 ms on the namespace's always cold Mesa cache ([status.md](status.md#ipc-latency)). `--latency-log FILE` appends one JSON line per run with each timed reply's send time and latency, the warm-up's latencies, the main threads' CPU time and, for each reply over 50 ms, what every thread of both Shingles was doing by /proc samples every millisecond (state, wait channel, system call), which serves as an off-CPU profile where perf is not allowed; it reads /proc only for the harness's own children. `SHINGLE_TRACE_TURNS=MS` makes any Shingle with the frontend (nested, offscreen, native) log each turn longer than `MS` milliseconds to stderr, `process` or `render`, with the time of each phase, its `CLOCK_MONOTONIC` start (the clock of Python's `time.monotonic`, to line it up with a harness's timestamps) and how long the loop was idle before it (crates/shingle-frontend/src/turn_trace.rs). It needs a readable and writable `/dev/fuse`; the mount lives only in the namespace. `tools/session_test/run.py --checks round-trip` instead runs session round trips without FUSE (tools/session_test/round_trip.py): five `wl_probe` clients in nested Shingle inside a headless one are arranged in a nested, unevenly weighted split with two floating views on two workspaces, and the layouts and views must be identical after a SIGKILL and restart and after a SIGTERM and restart. With `--master-binary PATH`, a `shingle` built from `master` (for example from `git archive master` in a directory of its own, built with its own target directory) saves the same layout as a version 1 session, which the build under test must restore unchanged and save back as version 2. `--checks slow round-trip` runs both. `--checks exit` (also on FUSE) checks that SIGTERM ends Shingle promptly while a session fsync is stuck: slowfs, here with `--threads` so that only the fsync is slow, holds every fsync for 20 s, a layout change follows the stuck write, and nested Shingle must exit with status 0 within 5 s with the last layout in the session file ([design/session-exit.md](design/session-exit.md)).

After those builds and `cargo build -p shingle-xwayland --example xw_probe`, `nice -n 19 tools/soak_test/run.py --mode headless|offscreen|nested --minutes N` soaks Shingle in the GPU harness's namespace: a seeded, repeatable cycle of client churn (wl_probe windows mapped, resized, floated, maximized, made fullscreen, minimized, moved between workspaces and closed over IPC; an output added and removed; vkcube; a `wl_probe --animate --presentation` for frame latency; xw_probe windows through lazy Xwayland; the clipboard between wl-copy, wl-paste and xclip both ways; drags from Wayland and X sources; a grim capture; Scale and Expo; headless leaves out what needs a frontend). Once a minute, when only its long-lived anchor window is mapped, it samples RSS, threads, fds and CPU time of each Shingle, `stipc/object_counts`, the namespace's CPU, the load, latency and, through `nvidia-smi` on the host, GPU memory, into `samples.csv` and `summary.md` under `target/soak/MODE-TIMESTAMP` (or `--output`). It fails on a crash, a panic in the log, a protocol error, a failed check, or growth flagged by its trend test (tools/soak_test/soak.py: after a five-sample warm-up the median of the last third must not exceed that of the first third by more than a tolerance, 8 MiB or 5 % of RSS, 3 fds, 2 threads, 32 MiB or 5 % of GPU memory and 3 of any count, with the fitted line agreeing). The Vulkan validation layer that debug builds load through wgpu is disabled for the run (`VK_LOADER_LAYERS_DISABLE=*validation*`) unless `--validation` is given, since its own bookkeeping grows the heap under the workload ([status.md](status.md#soak-tests)). It runs at niceness 19, waits while the 1-minute load is above 12 (`--load-limit`), and `--steps` runs some of a cycle's steps only, to find which one makes something grow. `python3 -m unittest` in tools/soak_test runs its tests. The native soak is step 53 of [native-testing.md](native-testing.md).

After `cargo build -p shingle-render --example staging_probe` too, `nice -n 19 tools/shm_bench/run.py` benchmarks shm commits in the same namespace: for offscreen Shingle and for nested Shingle inside offscreen Shingle, both on NVIDIA, and for each upload variant (`staging`, Shingle's staging buffers in system memory; `write_texture`, wgpu's `Queue::write_texture` with `SHINGLE_SHM_STAGING=0`; and with `--variants` also `staging_device_local`, the staging buffers in the PCIe BAR with `SHINGLE_SHM_STAGING=device-local`), a `wl_probe --animate FRAMES --presentation --size WxH [--damage-square SIDE]` draws each case of `--cases` (`WIDTHxHEIGHT:full` or `WIDTHxHEIGHT:SIDE`; 256x256, 1280x720 and 1920x1080 by default). Each row has the commit-to-presentation latency, the time and bytes of each upload from the buffer trace's `us=`, CPU per frame of the measured and the outer Shingle, the frame rate and, from `nvidia-smi` on the host, the GPU's performance state, clock, PCIe generation and BAR1 use while it ran; `staging_probe` times CPU writes into each host-visible memory type before and after. Results go to `results.md` and `results.json` under `target/shm_bench/TIMESTAMP` (or `--output`); `python3 -m unittest` in tools/shm_bench runs its tests. `SHINGLE_SHM_STAGING` is read when the GPU context is created ([status.md](status.md#shm-upload-speed)).

The native backend's hardware checks run on the dedicated test machine, never here ([native-testing.md](native-testing.md)). tools/native_test/bringup.py drives that machine from this host over the operator's own SSH: `report HOST` writes its hardware notes and the expected zero-copy path and cursor plane to target/bringup/HOST/report.md, `check HOST` prints the commands for whatever step 0 still lacks, `deploy HOST` builds `shingle` and `present_probe` here in release (`--jobs 2`, not above a load of 12) and copies them if the target's glibc and libraries fit, else builds the pushed commit there, `step N HOST` drives a step while Shingle runs on the machine's tty1 (started there with `shingle-tty1 --step N`, tools/native_test/start_tty1.py) and appends the result to target/bringup/HOST/results.md, and `collect HOST` copies the run back and checks it ([laptop-bringup.md](laptop-bringup.md#the-bring-up-driver)). Every subcommand refuses localhost and this host, by name, address, machine id and hostname, and the device steps also need `/etc/shingle-native-test-machine` on the target, so never point it at this host. `python3 -m unittest` in tools/native_test runs its tests, which replace SSH with a fake machine (tools/native_test/fake_machine.py), and `flake8 tools/native_test` checks it.

`.cargo/config.toml` limits Cargo to two jobs. Check `/proc/loadavg` before large builds, and run builds and test suites one after another rather than in parallel.

`wayland_toplevels_look_unchanged` (crates/shingle/src/wayland_pins.rs) compares what xdg toplevels look like from outside (IPC replies and events, configures, surface snapshots and sessions) with crates/shingle/testdata/wayland_pins.txt byte for byte. If a change is meant to alter that, rerun it with `SHINGLE_BLESS_PINS=1` and review the diff of the file.

## Wayfire's option table

A Wayfire import starts from the defaults in crates/shingle-config/data/wayfire-options.tsv, which tools/wayfire_options/generate.py writes from a Wayfire checkout's `metadata` directory. The table is checked in at the commit docs/design/wayfire-gaps.md pins; to move it, run `tools/wayfire_options/generate.py --metadata ../wayfire/metadata --commit SHA --output crates/shingle-config/data/wayfire-options.tsv` against a checkout at that commit, record the commit in the design document, and update the counts its tests expect. `python3 -m unittest` in tools/wayfire_options runs the generator's tests.

## Formatting

`rustfmt.toml` sets 80 columns and 2-space indentation:

```sh
cargo fmt --all
```

rustfmt leaves an entire expression untouched if it cannot fit one of its lines in 80 columns. After formatting, check `rg -n '.{81,}' crates --type rust`. Fix any hit by hand, with a `use` for long protocol paths, a helper for long `matches!` guards, or `concat!` for long strings, then format again.

Comments go on their own line above the code and use `//` or `///`, never `/* */`.

## Gloomy

WCM uses the Gloomy UI library from https://github.com/KRuskowski/gloomy, pinned to a commit in the root `Cargo.toml`. To change Gloomy, commit and push there, then bump the `rev` in its own Shingle commit.

To work on both at once, point Cargo at a local checkout without editing `Cargo.toml`:

```sh
cargo build --config 'patch."https://github.com/KRuskowski/gloomy".gloomy-core.path="../gloomy/crates/gloomy-core"' \
  --config 'patch."https://github.com/KRuskowski/gloomy".gloomy-app.path="../gloomy/crates/gloomy-app"'
```

## Running

```sh
cargo run --bin shingle -- --config data/shingle.yaml --spawn foot
cargo run --bin shingle -- --help
```

Inside a Wayland or X11 session this selects the nested backend and opens Shingle in a window, prints its private `WAYLAND_DISPLAY` and passes it to `--spawn` children. Every child Shingle starts gets the client environment (crates/shingle-session/src/environment.rs): Shingle's own `WAYLAND_DISPLAY`, its own `DISPLAY` and, with `--ipc`, `WAYFIRE_SOCKET`; the host's `DISPLAY`, `WAYLAND_SOCKET` and `WAYFIRE_SOCKET` never get through. Children also get Wayfire's `XDG_CURRENT_DESKTOP=wayfire` unless Shingle has one, `XCURSOR_THEME` and `XCURSOR_SIZE` from the cursor settings, and `WAYFIRE_CONFIG_FILE` for a Wayfire file, which replaces or removes the host's ([features.md](features.md#client-environment)); a nested Shingle started from the host Wayfire therefore passes the host's `XDG_CURRENT_DESKTOP` on. With the default `xwayland.mode: lazy`, Shingle binds the next free X display in `/tmp/.X11-unix` when it starts (`:2` beside the host session's `:0` and `:1`). `--headless` runs without a window. `--outputs N` starts headless and offscreen Shingle with `HEADLESS-1` to `HEADLESS-N`, and nested Shingle with a window for each; native lights every connected monitor it has a CRTC for, and at most N with the option. `--backend native`, and a start with none of `WAYLAND_DISPLAY`, `WAYLAND_SOCKET` and `DISPLAY` set, runs the native backend: it opens the seat with libseat and the input devices with libinput, so it is only ever run on the native test machine ([native-testing.md](native-testing.md)); from an SSH login without `XDG_SEAT` it refuses with "no seat" and status 1. Scripts and agents on a development host always pass `--headless` or `--backend nested`, so that a missing display variable can never select native. Bad options and unknown backends exit with status 2. The selection rules are in crates/shingle-bin/src/backend.rs and the [README](../README.md#running). Locking runs `shingle-lock` from `PATH`; set `SHINGLE_LOCK` to use another executable.

When testing nested from a session whose `XDG_RUNTIME_DIR` is replaced by a private one, set `WAYLAND_DISPLAY` to the host socket's absolute path so the window still reaches the host, and set `XDG_CONFIG_HOME`, `XDG_STATE_HOME` and `HOME` to private directories too. Outside the XWayland harness, also set `xwayland: {mode: false}` in the test config, so that nothing is bound in the host's `/tmp`.

## Real-client tests

Unit tests do not cover protocol behaviour end to end. For any protocol, IPC or session change, also test with real clients:

- Never stop or replace the host Wayfire session.
- Use a private `XDG_RUNTIME_DIR`, Wayland socket and IPC socket for each run.
- Exercise real protocol calls and check the resulting state changes; a successful build or import proves nothing.
- A harness that signals processes runs in a PID namespace (`unshare --pid --fork --mount-proc`) and checks every PID before signalling it: never signal a PID taken from a reply without checking it is positive, greater than 1 and the expected process, because `kill(-1)` reaches every process of the user.
- X11 clients run only inside `tools/xwayland_test/run.py`'s namespace, never against the host's X displays. Anything that needs the GPU's render node runs inside `tools/gpu_test/run.py`'s namespace, never with the host's card node, input devices or TTYs.
- Afterwards remove temporary fixture sources, binaries outside `target/`, sockets and logs. Leave `target/` itself in place.
- Record the result in [status.md](status.md), separately from what was only unit-tested.
